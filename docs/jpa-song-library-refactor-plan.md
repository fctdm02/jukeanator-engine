# Multi-tenant JPA song library + locationId-everywhere refactor — implementation plan

> **Note:** this is the pre-implementation plan, approved before Phases A–F were built (see the
> "JPA-backed song library + locationId-everywhere refactor" addendum at the bottom of
> [`multi-tenant-mode.md`](multi-tenant-mode.md) for what actually shipped, including a few
> deliberate deviations discovered during implementation — most notably, Phase A ended up using
> separate flat JPA row types rather than annotating the domain model classes directly, for reasons
> explained there. Kept here verbatim for the schema-design rationale and phase-by-phase reasoning,
> which may be useful for future investigation.

## Context

`jukeanator-engine` already has a substantial master/slave multi-tenant system built and verified (212 tests passing, documented in `docs/multi-tenant-mode.md`). But it took a "snapshot + proxy" shape: master serves song-library browse reads from a synced **JSON snapshot** on disk via a dedicated `SongLibraryServiceLocationProxy`/`SongQueueServiceLocationProxy`/`SongPlayerServiceLocationProxy` class family and parallel `LocationScoped*Controller`s, deliberately kept separate from the standalone/slave code path so standalone risk stayed at zero.

The goal now is a real pivot: give `SongLibraryRepository` a JPA/MySQL implementation (replacing the stub `SongLibraryRepositoryPostgresImpl`) where **one master database table set holds every location's songs**, tenant-separated by `locationId` — and use that to collapse the proxy/scoped-controller duplication entirely. Every relevant service method and controller takes `locationId` directly instead of having two parallel implementations. Standalone mode becomes "multi-tenant with exactly one location," not a structurally different code path. This is an accepted breaking change — existing persisted playlists/song-identifiers are obsolete and will be reset; there is no production master deployment yet, so schema and data are clean-slate.

## Decisions already confirmed (do not re-litigate during implementation)

1. **Unify library, queue, AND player** into one controller + one service class each, all under `/api/locations/{locationId}/...`. Each service internally branches: execute locally if `locationId` is this instance's own location, otherwise forward — queue/player via the existing `SlaveCommandGateway` (unchanged mechanism), library via a direct JPA query (no forwarding needed at all). This deletes `SongLibraryServiceLocationProxy`, `SongQueueServiceLocationProxy`, `SongPlayerServiceLocationProxy`, `LocationScopedSongLibraryController`, `LocationScopedSongQueueController`, `LocationScopedSongPlayerController`, and `LocationServiceRegistry`.
2. **Master memory model**: JPA-backed master fully materializes each location's library as an in-memory `RootFolderEntity` tree (same object graph/search/ranking logic reused verbatim), held in `Map<Integer, RootFolderEntity> songLibraryRoots`. The `SongLibraryRepository` field itself stays **singular** (one JPA repository, queries filtered by `location_id`) — Item 3's literal "Map of repositories" is implemented as a map of loaded **roots**, not repository instances, since one datasource already serves every tenant.
3. **Sync transport unchanged**: keep the existing `LibrarySnapshotDto` JSON snapshot mechanism (already built, version-safe) for slave→master sync — no raw `.oos` transfer. When `song-library.repository-type=jpa`, the sync handler populates the new JPA tables from the snapshot DTO instead of writing `library.json`. Cover art multipart upload is unchanged either way. Filesystem-mode-on-master needs no new work — the existing JSON snapshot write already satisfies Item 2's "preserve the location's data on master's disk" intent.
4. **Clean slate**: no real production data to migrate. New Flyway migrations are additive (`V3`, `V4`, ...) rather than editing `V1`/`V2` in place.
5. **Unscoped legacy paths removed**: `/api/song-library/**`, `/api/song-queue/**`, `/api/song-player/**` (no `locationId`) go away entirely once every method takes `locationId` — no aliasing. The Swing UI calls services in-process, not over HTTP, so nothing external in this repo depends on the old paths.
6. **Song-player is in scope**: unify it alongside library/queue in this same effort (not deferred), since it's the same mechanical pattern as queue (branch: local vs. forward-via-`SlaveCommandGateway`) and its `LocationScopedSongPlayerController`/`SongPlayerServiceLocationProxy` already exist as the mirror of the queue ones.

## Schema design (the hard JPA problem)

The literal ask — `PRIMARY KEY (LocationId, AlbumId, SongId)` on "the song table" — can't be the actual JPA `@Id` once folders and files are modeled as `SINGLE_TABLE` inheritance hierarchies: `RootFolderEntity`/`GenreFolderEntity`/`ArtistFolderEntity`/`AlbumFolderEntity` share one folder table, and Root/Genre/Artist rows have no natural `(locationId, albumId, songId)` tuple. Recommended design: reuse the existing `AbstractPersistentEntity` surrogate-id pattern (`persistent_identity`, `GenerationType.SEQUENCE`, same `persistent_identity_seq` generator already used by `users`/`locations`) as the real JPA `@Id` on both new tables, and enforce the tenant-scoped uniqueness the literal ask wants via a `UNIQUE` constraint instead:

**`song_library_folders`** — `SINGLE_TABLE` inheritance for the `FolderEntity` hierarchy (discriminator `folder_type`: `ROOT`/`GENRE`/`ARTIST`/`ALBUM`). Columns: `persistent_identity` (PK), `location_id` (FK → `locations`), `folder_type`, `parent_folder_id` (self-FK), `source_id` (the slave's scan-local id from `SongScanner`; null for `ROOT`), `name`. `UNIQUE (location_id, folder_type, source_id)`. `ArtistFromSongEntity` is **not** persisted — it stays a purely in-memory derived view rebuilt by `RootFolderEntity.initialize()`, exactly as it works today for the filesystem repository.

**`song_library_files`** — `SINGLE_TABLE` inheritance for the `AbstractFileEntity` hierarchy (discriminator `file_type`: `SONG`/`ALBUM_COVER_ART`/`ALBUM_METADATA`/`LOCATION_METADATA`). Columns: `persistent_identity` (PK), `location_id`, `parent_folder_id` (FK → the owning album/root folder), `file_type`, `source_id` (slave-local song id, null for the three singleton file types), `name`, plus per-type columns (`artist_name`/`song_name`/`track_number`/`num_plays` for SONG; `genre`/`cover_art_url`/`record_label`/`release_date`/`has_explicit` for ALBUM_METADATA; `location_name`/`logo_name`/`latitude`/`longitude`/`is_geo_fenced` for LOCATION_METADATA). `UNIQUE (location_id, parent_folder_id, file_type, source_id)` — this is what actually delivers "no two rows can claim the same (location, album, song)."

IDs in both tables are **scan-local** (`SongScanner`'s per-slave sequential ints), never merged across locations — matches the existing documented invariant ("master must never merge multiple slaves' libraries into one ID space"). `getAlbumById`/`getSongById` etc. keep taking the same plain ints as today; nothing about the public DTO/API shape changes from this schema choice.

**Known sharp edge to preserve**: `AbstractLibraryEntity.getNaturalIdentity()`/`existsOnFilesystem()`/cover-art disk-path methods are meaningless on a JPA-hydrated master root (no real files ever land on master's disk, only metadata syncs). The existing proxy code already avoids calling these for remote data (e.g. explicitly passes `coverArtPath = null`); the unified service/mapper code must preserve that same discipline.

## Phase breakdown

### Phase A — JPA entities, repository, Flyway migrations (Item 1)
- Add JPA annotations (`@Entity`, `@Inheritance(SINGLE_TABLE)`, `@DiscriminatorColumn`/`@DiscriminatorValue`) to the folder and file entity hierarchies in `domain/songlibrary/model/`.
- New `domain/songlibrary/repository/SongLibraryRepositoryJpaImpl.java`, mirroring `UserRepositoryJpaImpl.java`'s shape (`EntityManagerFactory`/`PlatformTransactionManager`). `loadAggregateRoot(int locationId)` queries both tables `WHERE location_id = ?` and reassembles the tree, then calls `root.initialize()` — same contract as the filesystem loader. `storeAggregateRoot(root)`: delete-then-bulk-insert all rows for that `location_id` in one transaction (simpler and correct here since the tree is always fully materialized before a store, unlike `UserRepositoryJpaImpl`'s diff/orphan-delete approach).
- **Delete** `SongLibraryRepositoryPostgresImpl.java`. Rename the `song-library.repository-type` value `postgres` → `jpa` throughout `AppConfig.java` and all `application*.yml`/`docs/application-*-mode.yml` files.
- `SongLibraryRepositoryFileSystemImpl.loadAggregateRoot(int)` (currently throws unsupported) gets a real implementation: move the existing "find the one `.oos` file under `basePath`" logic (today living in `SongLibraryServiceImpl.findMostRecentOosFile()`) down into the repository, ignoring the passed int (filesystem mode is always single-location). This is what lets the unified service call `loadAggregateRoot(locationId)` uniformly regardless of repository type.
- New migrations: `src/main/resources/db/migration/{postgresql,mysql}/V3__init_song_library_schema.sql` (both dialects, following `V2__init_location_schema.sql`'s existing Postgres/MySQL delta pattern).

### Phase B — `SongLibraryServiceImpl`/`SongLibraryController` unification (Items 2–4, part of 6)
- `SongLibraryService` interface: every "USER ROLE" method gains `Integer locationId` as the first parameter (the 13 methods Item 4 lists, plus `getSongLibraryRoot(Integer locationId)`). Admin/scan/stats methods (`scanFileSystemForSongs`, `resetSongStatistics`, etc.) stay locationId-less — scanning is inherently local to whichever instance owns the physical files.
- `SongLibraryServiceImpl` fields: keep `private final SongLibraryRepository songLibraryRepository;` singular; add `private final Map<Integer, RootFolderEntity> songLibraryRoots = new HashMap<>();` and `private Integer ownLocationId;` (null on master). Replace `initialize()` with a `getOrLoadRoot(Integer locationId)` that lazily loads-and-caches via `songLibraryRepository.loadAggregateRoot(locationId)`. On standalone/slave boot, resolve the real `locationId` from the loaded root's `getMetadata().getLocationId()` (filesystem mode) or from `AppProperties.getLocationId()` up front (JPA mode needs a real id before it can query — filesystem mode can discover its one file without knowing the id first).
- `SongQueueServiceImpl.initializeInternal()`'s `getSongLibraryRoot()` call becomes `getSongLibraryRoot(ownLocationId)`.
- Controller: delete `LocationScopedSongLibraryController.java`; `SongLibraryController` moves to `@RequestMapping("/api/locations/{locationId}/song-library")` with `@PathVariable Integer locationId` added to every method. Cover-art endpoint branches: own location → serve from `AlbumFolderEntity`'s disk path (standalone/slave); other location → serve from `LocationService.getCoverArtPath(locationId, albumId)` (master), same as today's split logic just merged into one method.
- **Delete** `SongLibraryServiceLocationProxy.java`, `LocationScopedSongLibraryController.java`.
- Downstream call-site updates: `SongQueueServiceImpl`, and the 8 Swing UI classes calling `SongLibraryService` in-process (`GenreDetailPanel`, `GenrePanel`, `JukeANatorFrame`, `SearchPanel`, `HomePanel`, `HotHerePanel`, `EditAlbumCard`, `AdminPanel`) — each passes its own `ownLocationId`, sourced from a new small `SongLibraryService.getOwnLocationId()` accessor rather than re-deriving it independently in each Swing class.

### Phase C — `SongQueueServiceImpl`/`SongQueueController` unification (Item 6 for queue)
- `SongQueueService`: every mutating/query method gains `Integer locationId` first param. The 4 `@PublicServiceMethod` system methods (`dequeueNextSong`, `isQueueEmpty`, etc.) stay as-is — only ever called by this instance's own local player/coordinator, which per `NotMasterModeCondition` never exist on master.
- `SongQueueServiceImpl`: each public method branches — `isOwnLocation(locationId)` ? run the existing local logic unchanged : `slaveCommandGateway.sendCommand(locationId, "methodName", payload, ResponseType)`.
- This forces `SongQueueServiceImpl` itself onto master (today it's excluded there via `NotMasterModeCondition`). Master's instance needs harmless stand-ins: a new `NoOpBackgroundMusicService` (`isEnabled()` always false) wired as a master-only `@Bean`, and `SlaveCommandGateway` as an optional/nullable constructor dependency. `SongQueueRepository` can stay wired unconditionally — on master the local-execution branch (the only branch that touches it) never runs.
- Controller: delete `LocationScopedSongQueueController.java`; `SongQueueController` drops its `@Conditional(NotMasterModeCondition.class)`, moves to `@RequestMapping("/api/locations/{locationId}/song-queue")`. **Preserve as an explicit branch, not merge away**: today's credit-charging split (event-driven `SongAddedToQueueEvent` listener for local adds vs. explicit `userService.chargeCreditsForQueueAction(email, priority, locationId)` for remote adds, because a remote add's mutation happens on the slave's process and its domain event never crosses processes) — getting this branch wrong double-charges or under-charges credits.
- **Delete** `SongQueueServiceLocationProxy.java`, `LocationScopedSongQueueController.java`.

### Phase D — `SongPlayerServiceImpl`/`SongPlayerController` unification (confirmed in-scope addition)
Same mechanical pattern as Phase C, smaller surface (`getNowPlayingSong`, `getPlaybackStatus`, `playNextTrack`, `pause`, `stop`, `lockQueue`, `unlockQueue` gain `Integer locationId`; the 2 `@PublicServiceMethod` event-handler methods stay as-is). `SongPlayerServiceImpl` becomes constructible on master too — verify its actual constructor dependencies during implementation (likely needs the same kind of no-op stand-in as `NoOpBackgroundMusicService` for any hardware/audio-coordinator dependency, since master's branch always forwards and never touches real audio). Delete `SongPlayerServiceLocationProxy.java`, `LocationScopedSongPlayerController.java`. `SongPlayerController` drops `NotMasterModeCondition`, moves to `/api/locations/{locationId}/song-player`.

> **What actually shipped differs here**: `SongPlayerServiceImpl`'s constructor has real side effects (spins up a VLC/Winamp process, starts a watchdog thread) that must never run on master, so it stayed a separate class from a new `SongPlayerServiceMasterImpl` rather than merging into one locationId-branching class the way the queue service did. See the addendum in `multi-tenant-mode.md` for the final shape.

### Phase E — `SongIdentifier` + `LocationServiceRegistry` removal (Item 5, rest of 6)
- `SongIdentifier` (`@Embeddable`) gains `Integer locationId` alongside `albumId`/`songId`; update constructor, `equals`/`hashCode`/`toString`. Flyway `V4` (both dialects) adds `location_id INTEGER` to the `user_song_play_history` and `playlist_songs` element-collection tables, plus a clean-slate `DELETE FROM` on both (existing rows are obsolete per your confirmation).
- Update all `new SongIdentifier(...)` call sites: `SongQueueServiceImpl.addAlbumToQueue()`, `SongQueueServiceImpl.loadPlaylistIntoQueue()`, `UserEntity.addSongToPlaylist`/`removeSongFromPlaylist` (via `UserServiceImpl`, which needs its own `locationId` threading for playlist operations — a necessary, if not originally enumerated, downstream file).
- **Delete** `LocationServiceRegistry.java` entirely now that all three proxy families are gone (Phases B–D make this safe, unlike deferring song-player).

### Phase F — slave→master sync populates JPA (Item 2's "master fills its DB")
- `LocationServiceImpl.receiveLibraryMetadataSync()`: when `song-library.repository-type=jpa`, build a `RootFolderEntity` tree from the incoming `LibrarySnapshotDto` (same field mapping `SongLibraryServiceLocationProxy` already does today for read-serving) and call `songLibraryRepository.storeAggregateRoot(root)` instead of writing `library.json`. Requires injecting `SongLibraryRepository` into `LocationServiceImpl`. Filesystem-mode master keeps today's JSON-write behavior unchanged — this is unconditional across repository types (a filesystem-storage concern for images/files, orthogonal to whether catalog data is queried from JPA or a JSON snapshot).
- Metadata (genre, cover art URL, record label, release date, etc.) travels as structured `LibrarySnapshotDto`/DB-column fields only — no standalone `metadata.txt`-style files are written to master's disk. Consistent with the existing JSON-snapshot-transport decision (one representation of the data, not two divergent ones).
- **Make the sync explicitly background/async**: `LibrarySyncService.handleScanFileSystemForSongsEvent()` currently calls `syncLibrary()` (which both POSTs the metadata snapshot and uploads any stale cover art) synchronously, inline on the same thread as the scan itself — confirmed by reading `LibrarySyncService.java:56-69`, whose own comment explains the broad `catch (Throwable t)` is there specifically because a slow/unreachable master must never fail or delay the slave's own scan. Per your explicit ask, wrap this dispatch so the HTTP round-trip(s) run on a background thread instead of blocking the scan's calling thread — e.g. `ExecutorService.submit(this::syncLibrary)` via a dedicated single-thread executor field, mirroring the existing `storeSongLibraryAsync()` pattern in `SongLibraryRepositoryFileSystemImpl`. The existing per-album, hash-diffed cover-art upload loop (`syncLibrary()` → `uploadCoverArt()`, only for albums the master reports as missing/stale) already does everything needed for "upload all cover art images... to a locationId-scoped directory underneath the location's data directory" — including on first registration, since nothing has synced yet and every album will report as needing cover art — so no separate bulk/initial-registration process is needed beyond this async change.
- Once this lands, master's `getOrLoadRoot(locationId)` (Phase B) transparently serves freshly-synced locations via the normal JPA path — no separate proxy needed, confirming decision #1.
- The master-id-handoff handshake (`StompLocationApiKeyChannelInterceptor`, `LocationEventStompController`, `SlaveConnectionManager`) is already fully built — nothing new needed there.

## Config changes
- `AppConfig.java`: rename `songLibraryRepositoryPostgresImpl` bean → `songLibraryRepositoryJpaImpl`, `@ConditionalOnProperty(havingValue="jpa")`, constructed like `userRepositoryJpaImpl`. Drop `@Conditional(NotMasterModeCondition.class)` from the `songQueueService`/`songPlayerService` bean definitions; add master-only no-op stand-in beans (`NoOpBackgroundMusicService` and the player equivalent).
- `application.yml` / environment-specific yml / `docs/application-*-mode.yml`: `song-library.repository-type: postgres` → `jpa` wherever present.
- `LocationConfig.java`: remove the `LocationServiceRegistry` bean method.

## Risk callouts
1. **Large test surface**: `SongLibraryServiceTest`, `SongLibraryControllerTest`, `SongQueueServiceTest`, `SongQueueControllerTest`, `SongPlayerServiceTest`, `SongPlayerControllerTest`, `RootFolderEntityTest`, `AbstractSongLibraryEntityTest`, `SongScannerTest`, `LocationServiceTest` all call methods gaining a `locationId` parameter — every call site needs updating, not just production code.
2. **`MySqlJukeanatorEngineApplicationTests`/`MySqlMasterModeJukeanatorEngineApplicationTests`** (Testcontainers, currently skipped without Docker) are the only tests that load a full master-mode Spring context touching this — must be run against real Docker at least once, since master now constructs `SongQueueServiceImpl`/`SongPlayerServiceImpl` for the first time ever (previously excluded by `NotMasterModeCondition`) and a missing/circular dependency would only surface there.
3. **Hot-path store cost**: `handleSongAddedToQueueEvent()` triggers `storeSongLibraryAsync()` on every song play; the JPA impl's delete+reinsert-whole-tree approach is wasteful for that specific call. Acceptable for this refactor; flag as a follow-up optimization (targeted `UPDATE ... SET num_plays`), not blocking.
4. **`SongScanner`'s genre/artist index counters** need a close look during Phase A implementation to confirm they don't collide with the proposed `UNIQUE (location_id, folder_type, source_id)` constraint.
5. Recommend prototyping Phase C/D's master-side `SongQueueServiceImpl`/`SongPlayerServiceImpl` construction (one command round-trip) before writing every forwarding branch — same "prototype first" caution the original multi-tenant doc used for `SlaveCommandGateway`.

## Verification
- After Phase A: `mvn clean compile`/`test-compile` against both dialects; a targeted test round-trips a `RootFolderEntity` through `SongLibraryRepositoryJpaImpl.storeAggregateRoot`/`loadAggregateRoot` and confirms the reloaded tree matches (genres/artists/albums/songs, `num_plays`, metadata fields).
- After each phase: full `mvn test`; standalone-mode smoke test (default `application.yml`) to confirm browse/queue/player/credit-charge behavior is unchanged from a user's perspective, just with `locationId` now required everywhere.
- After Phase C/D: spin up one `master` + one `slave` instance locally, confirm a `POST /api/locations/{id}/song-queue/addSong` round-trips through the slave's real queue and back, and confirms a clean `LocationOfflineException`/503 when the slave connection is killed mid-request.
- After Phase F: confirm `song-library.repository-type=jpa` on master — provision a location, trigger a scan on a `jpa`-mode-or-not slave, confirm rows land in `song_library_folders`/`song_library_files` tagged with the right `location_id`, and `GET /api/locations/{id}/song-library/albums` serves them correctly.
- Explicitly run the Testcontainers-based `MySql*ApplicationTests` against real Docker before considering this done (risk #2).
